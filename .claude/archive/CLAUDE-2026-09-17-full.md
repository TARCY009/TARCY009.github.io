### トップページの「GO」のOに方位磁針の針（2026-09-04・タダシさん指示）

サイトアイコン（GOのOが方位磁針）と看板の「GOナビ」がつながって見えるよう、**看板のOの穴の中にも同じ針**を入れた
（「そこを統一していないとアイコンとの関連性が全くない」）。図柄はロゴと同じ: マゼンタ`#ff5abe`の針＋青灰`#8c98c6`の後ろ半分＋白い中心、
向きは右上（SVGで`rotate(38 50 50)`）。実装は `index.html` の `h1 .o`（Oだけを包む inline-block・**自分の塗りを持たせる**）＋
`h1 .ndl`（絶対配置のSVG・幅高さ.46em・`pointer-events:none`）。

- **位置は字形を実測して決めた**（ブラウザのcanvasで禅角ゴシックNew 900の「O」を描いて穴の範囲を走査）:
  穴は横0.17〜0.55em（中心0.36em）・縦は基線から0.12〜0.59em（中心0.355em）。箱は幅＝字送り0.726em＋字間0.1em、
  高さ＝行送り1.12em、基線は上から0.94em → **`left:calc(50% - .05em)`・`top:calc(50% + .025em)`**
- 端末に禅角ゴシックが無くヒラギノに落ちたときは、穴の位置が少しずれる可能性がある（許容。取り寄せは wordmark.css が持つ）
- **⚠ 2026-09-04同日に作り直し: 針は h1 の「外」に置く**。最初は O の中（`h1 .o` の子）に入れたが、h1 には金属加工＝
  7段の drop-shadow フィルターと background-clip:text がかかっており、その中の SVG が **iPhone の Safari で描画に失敗して
  ページが黒→白（クラッシュ）**になった（タダシさん報告「どのツールもスマホで見れない」＝トップが開けず全ツールへ行けない）。
  いまは h1 を `.wmbox`（inline-block・position:relative）で包み、針 `.ndl` はその中の絶対配置＝フィルターの外。
  位置は読み込み後に JS（`placeNeedle`）が「O」の実際の矩形から計算する（穴の中心＝左から0.36em×1.04・箱の上から0.525em）。
  **フィルター付き・clip:text の要素の中に、位置指定の要素や SVG を入れない**（恒久）
  - **⚠ 「どのツールもスマホで見れない」の本当の原因は iPhone の電波が謎に落ちていたこと**（電源を落として復旧・タダシさん報告）。
    コード側の問題ではなかったが、上の作り直し（針をフィルターの外へ）は安全側なのでそのまま採用
  - **針の位置は書体が届いたあとに必ず計算し直す**（2026-09-04タダシさん報告: iPhoneで針がOの左上の縁に付いていた）。
    最初の1回だけ計算すると、代替書体の字形で決めた位置に針が残る。`document.fonts.ready`／`loadingdone`／`load`／`resize`／
    `pageshow`／`ResizeObserver(h1)`＋念のための後追い（0.3〜5秒）のすべてで `place()` を呼ぶ（位置を上書きするだけなので何度呼んでも害はない）
  - **⚠ それでも直らなかった（2026-09-08タダシさん報告「前のバグった状態に戻っている」）→ 穴の位置を決め打ちしない**。
    計算し直しても、使っていた数字（左0.36em・基線から0.355em上）が**禅角ゴシックNewの字形の実測値**なので、
    **書体が届かない・取り寄せに失敗した端末では代替のヒラギノの「O」（穴は左0.45em・0.39em上）に禅角の位置で置かれ、
    穴の左上の縁に付く**（＝報告の症状そのもの）。いまは `place()` が**その時点で画面に出ている書体の「O」を canvas に描いて
    穴の範囲を走査**し（`holeOf`）、その中心に置く。基線は O の直後に置いた**高さ0の印 `h1 .bp`** の座標から取る
    （書体の上端の数値も推測しない）。`.go` の横1.04倍は `DOMMatrix` で読む。走査できない環境だけ禅角の実測値に落ちる。
    検証: 禅角=0.377em/ヒラギノ=0.468em（=0.45×1.04）と、どちらも穴の中心に一致。
    **⚠ ローカルのブラウザパネルが非表示だと `ResizeObserver` が一切発火しない**ので、書体を差し替えたあとは
    `window.dispatchEvent(new Event('resize'))` で計算し直してから測ること（発火しないのを「バグ」と誤読しかけた）

### 全ツールのタイトル文字（2026-09-04確定・完成）

**ダーク＝真っ白＋ツールごとの明るい色／ライト＝そのツールの色のベタ塗り**。金属加工・グラデーションは
**一切なし**（下の経緯参照）。書体は全ツール**Noto Sans JP 900**。定義は **`assets/wordmark.css` 1か所**
（`build_wordmark.py`の出力・手で編集しない）。

ページ側がやることは2つ（新ツールでも同じ）:

1. `<head>` に `<link rel="stylesheet" href="/assets/wordmark.css">`（explain.css の直後）
2. ツール名の要素に **`class="wmk" data-tool="<キー>"`**（キーごとの色は wordmark.css が持つ）。
   「◯◯オススメツール」「◯◯対策ツール」のように決まり文句が付くタイトルは、
   その部分だけ **`class="wmksuf"`** の別要素に分けて白のまま残す
   （例: `<span class="wmk" data-tool="gym-defense">ジム防衛</span><span class="wmksuf">オススメツール</span>`）。

**教訓**: ①色の調整は**hexの数値だけで「明るいはず/違って見えるはず」と判断しない**。
同じ画面内の他の文字と並べたスクショを実際に見て判断すること。②要望には**「何をやめてほしいか」と
「何を残してほしいか」の両方がある**。「明るくして」だけを読んで手段（グラデーションか、ベタ塗りか）を
勝手に決めない。③**微妙な差を画像比較で選ばせる進め方は、5段階試しても1つも刺さらなかった**。
次に同種の色調整を頼まれたら、**小さな差を比べさせる前に、まず具体的でシンプルな案（今回なら
「白＋ツールごとの色を半分ずつ」）をこちらから早めに出す**こと。④**「戻して」には2種類ある**——
「直前のコミットの値に戻す」だけでなく「その変更を始める前の"体験"に戻す（＝機能ごと後退する）」を
指すこともある。曖昧なら、範囲を確認するかユーザーが示した具体案をそのまま採用するほうが早い。
⑤**ユーザーが具体的な代替案を提示してきたら、それが「分からなければ」の保険であっても、
以降の試行錯誤より優先してすぐ採用してよい**（今回は代替案の実装だけで一発で解決した）。

`.wmk`（クラス1つ・詳細度0,1,0）と`.tool`（同じく詳細度0,1,0）は**詳細度が同点**になるため、
**後から読み込まれるほう（ページ自身の`<style>`。wordmark.cssより後）が勝つ**。
**ライトモードは`:root.light .wmk`の詳細度が高くて問題が隠れていた**が、**ダークモードだけ
旧グラデーションのまま**になっていた（画面を見比べないと気づけない・実際に本番で発覚した）。
**新ツールに`.wmk`を足すときは、その要素に色を付けている既存のCSSルールを必ず探して消すこと**
（`grep -n "header h1\|\.tool{\|h1 b{\|h1 span{"` などで見出し要素の背景・色指定を洗い出す）。

**⚠ ライトモードの文字色のコツ（2026-09-03タダシさん・恒久）**:

> **うっすらとした背景のときは、文字色も背景と同じ系統の濃い色にすると、雰囲気を壊さずに馴染む。**
> **ただし薄すぎると背景に溶け、濃すぎると浮く。ちょうどいい濃さを出すのがいちばん大事。**

**この作業で踏んだ落とし穴（同じ失敗を繰り返さないこと）**:

1. **大きい字と小さい字でレシピを分ける**。トップページの看板は44px、ツール名は18〜24pxと2.5倍違う。
   看板用の金属加工（中央の反射の折れ目・4段の押し出し・輪郭）を小さい字に流用したら、
   **折れ目が1px以下の汚い線**になり、押し出しがにじみ、輪郭がぼけた。
   タダシさんの評: **「全然トップページのタイトルと違うよ！」**
2. **暗い側を「黒」に寄せると色味が死ぬ**。マゼンタも金茶も深緑も同じ暗い色に潰れて、
   **どのツールも文字色が同じに見える**。暗い側は**色味を残した濃さ**にする
3. **変形（`transform`）をかけた部分には、親の `background-clip:text` の塗りが届かない**。
   「GO」を横に伸ばした瞬間に**塗りが消えて輪郭だけ**になった。変形する要素には**同じ塗りを自分にも持たせる**
4. **輪郭は塗りの「下」に回す**（`paint-order:stroke fill`）。上に重ねると太らせたとき内側が食われて筒に見える
5. **厚みは `text-shadow` で作る**（`filter` は使わない）。filterだと h1 の中の
   バッジや添え書きにまで影が乗る
6. **押し出しは文字より暗い色**にする。明るい銀にすると文字のまわりが白くにじんで輪郭がぼやける

### テスターのフィードバックを集める仕組み（2026-09-06実装・タダシさん指示）

**Xでテスターを募る → 10名ほどにDMでURLを送る → 全ツールを試してもらい、気づいたことをその場で送ってもらう**
という流れを作るためのもの。**タダシさんは特設ページで読んで、そのまま Claude Code に貼るだけでよい**のがねらい。

**このサイトはサーバーを持たない静的サイト**なので、文章とスクリーンショットの受け口だけは外の仕組みを借りる。
**Tally（フォームサービス）を使う**——無料でファイル添付（10MBまで）とGoogleスプレッドシート連携ができ、
**テスターはログイン不要**。Googleスプレッドシート＋スクリプト方式も検討したが、
**「安全ではないページ」の警告画面を通る手順があってタダシさんの手間が大きい**ので取り下げた。

**送る側＝共通部品 `assets/feedback.css` / `assets/feedback.js`**（theme・explain・home と同じ自己完結の流儀）。
ページ側の追加は2行だけ（新ツールでも同じ）:

1. `<head>` に `feedback.css` を読み込む（`home.css` の直後）
2. **`home.js` の直後**に `feedback.js` を読み込む

- **設定は `feedback.js` の先頭4つだけ**: `FORM`（フォームのURL・**空のあいだは何も出さない**＝入れ忘れても本番が壊れない）／
  `UNTIL`（この日を過ぎたら自動で消える＝「期間だけ出す」）／`ALL`（`false`＝案内のURLを開いた人だけ・`true`＝全員）／
  隠しフィールドの名前 `tool`・`ctx`
- **⚠ `?fb=1` は `location.search` だけを見て判定してはいけない**（実際に踏んだ）。
  GBL・ロケット団・対戦記録は**自分で住所を書き直すツール**で、その処理が `feedback.js` より
  先に走るため、読むころには `fb=1` が消えている。**「最初に開いた住所」
  （`performance.getEntriesByType('navigation')[0].name`）も一緒に見る**ことで、
  ページごとの読み込み順に左右されなくなる（ページ側に3行目を足さずに済む）
- **⚠ 案内は全員には出さない**（既定 `ALL=false`）。サイトは公開中なので、全員に出すと
  一般の訪問者にもテスト中の表示が見えてしまう。**DMに貼るURLの末尾に `?fb=1` を付ける**と、
  その人の端末に印（`site_feedback`）が残って**全ツールでボタンが出る**。
  **`?fb=1` は読み込んだ直後に住所から消す**（残すと、その人が共有したリンクから案内が広がる）
- **出す場所はトップページと全ツール**（タダシさん選択）。トップは大きなバナー、ツールは細い帯。
  **不具合に気づいたその場で送れる**ので「あとでトップに戻って書く」必要がなく、
  **どのツールの話か・そのときの設定（URL）を自動で拾える**
- **一緒に送る情報**（テスターは書かなくてよい）: ツール名（`tool`）と、
  端末／ブラウザ・画面の大きさ・テーマ・日時・**そのときのURL**をまとめた1行（`ctx`）。
  GBLなどURLに設定が入るツールは**そのURLを開くだけで同じ状態を再現できる**
- **見た目は金**（サイト本来の役割色＝レイド赤・対戦水色・調べる紫とは別）。
  **一時的な案内**だと色で分かるようにするため。トップページの決めごとに合わせて**絵文字は使わない**

**⚠ 狭い画面では「テスト中」の札を出さない**（`.fbbar:not(.big) .fbtag`）。
札を残すと、**ページ自身の左右余白が広いツール（個体値チェッカーは16px）でだけ**文章が折り返して
2段になり、ページごとに帯の高さが揃わなくなる（実際に踏んだ）。
**逆に自分の左右余白（10px）を外してもいけない**——ページ自身に左右余白が無いツール
（GBL・図鑑・マックスバトル・ブレイクポイント）で帯が画面の端に貼り付く（これも踏んだ）。
実測: 375px幅で**全13ページとも高さ47px・横はみ出し0**、320pxでは自然に2段になる。

**読む側＝特設ページ `/feedback/`**（管理用・`noindex`・トップページのツール一覧には載せない）:

- **⚠ 読み込み先のCSVのURLはファイルに書かない**（2026-09-13）。以前は `CSV_URL` にそのまま書いていたが、
  このサイトのファイルはGitHubで誰でも見られるので、**届いた内容（お名前・本文・スクリーンショットのリンク）が誰でも読める状態**だった。
  いまは画面の「読み込み先のURL」欄から**端末のブラウザにだけ保存**する（localStorage `feedback_csv_url`）。
  過去のURLはGitHubの更新履歴に残るので、**スプレッドシートを作り直して新しいURLにする**必要がある（タダシさんの作業）
- **お問い合わせ（`/contact/`）も同じフォームに届き、ここに並ぶ**（ツール名の欄が「お問い合わせ」）。公開後もここで読む。
  お問い合わせには**個別の返事はしない**（フォームに連絡先の欄が無いため。ページの文言も「お返事はしていません」）

- 読み込みは2通り。**①公開したスプレッドシートのCSVを自動で読む**（`CSV_URL` に入れる）／
  **②その中身を貼り付ける欄**。②を必ず用意してあるのは、公開CSVは通信の制限で読めないことがあるため
  （読めなければ自動で貼り付け欄が開く）
- **⚠ 通し番号の列（Submission ID・Respondent ID）は「いちばん先に」外す**（実際に踏んだ）。
  あとから外すと、日時の列を探すときに **「Submission ID」の中の submission を掴んで**、
  送信日時のかわりに通し番号が出る
- **日時は `ctx` に入れてある「テスターの端末の時計」を使う**。フォームサービスの
  「Submitted at」は**世界標準時**なので、日本だと9時間ずれて読みづらい
- **列の名前は決め打ちしない**。`tool`・`ctx`・日時の列は見出しから、
  残りは**中身から**見分ける（URLが並ぶ列＝スクリーンショット／いちばん長い文章の列＝本文／短い列＝名前）。
  フォームの質問文をあとから変えても壊れない。**どれにも当てはまらない列は「その他」として必ず出す**（取りこぼさない）
- **「この1件をコピー」で、そのまま Claude Code に貼れる形**になる
  （見出し・送信日時・環境・スクリーンショットのURL・本文）。「まとめてコピー」もある
- **確認した印**（`feedback_done`）で既読を隠せる。既定は「まだ見ていないものだけ」
- **⚠ ライトの土台は `:not([aria-pressed="true"])` で限定する**。限定しないと詳細度で点灯に勝ってしまい、
  **ライトだけ点灯しなくなる**（このサイトで何度も踏んでいる落とし穴・ここでも踏んだ）
- **⚠ 画像が読めなかったときは `onerror` でURLの文字に切り替える**。そうしないと112pxの空箱が残る

**長押し照準の説明ウィンドウ（2026-08-15実装・タダシさん発案の操作）**:

💡ONのあいだ、**説明を持つ部品（`title` 属性 or `data-help` 属性）を長押しすると照準モード**に入り、
指の位置の部品が水色に光って説明ウィンドウ（`#exptip`）が指の上に出る。
**指をタップしたままスライドすると照準が別の部品へ移り、ウィンドウが差し替わる**。
指を離すとウィンドウは残り（読めるように）、次にどこかをタップすると閉じる。
パソコンはマウスを乗せるだけで同じウィンドウが出る。実装はすべて `explain.js`/`explain.css`。

- **説明文は各ページがもともと持っている `title` 属性をそのまま使う**（スマホでは今まで見る手段が
  無かったツールチップの再利用）。新しく書くときは `title` でも `data-help` でもよい
- **タイプアイコン(.tbadge)は説明の対象にしない**（2026-08-15タダシさん指示。絵を見ればわかるため）。

  - **メガLvの並びに「＋わざの威力だけ変わります」を添える**（共通部品 `mega-lv.js` の中に持たせたので全ツール共通）

    **「PLはLv4なのに＋わざはLv2」という実際にはありえない状態**を作れてしまう
  - 置き場所は**名前・個体値のすぐ下（PLの行の上）**で、注記「＋わざの威力」を添える。

    **PL上限ボタンの表記（メガLv4／メガLv4＋相棒）は全ツール統一の確定表記なので変えない**
- **⚠ メガレベルで結果が変わるのは「＋わざが採用された行」だけ**。同じポケモンでも、
  ボスのタイプ相性しだいで別のわざが選ばれれば**レベルを変えても数字は動かない**（これは正しい動き）。
  さらに**＋わざは13本とも1ゲージ**なので、**「分割SP優遇」をONにしているあいだ**は
  低いレベルで分割あり技に差し替わることもある（OFF＝既定なら火力順のまま）。
  **⚠ どちらも「相手のタイプしだい」で、ポケモン単位では決まらない**（2026-09-01にタダシさんの指摘で訂正）。
  実例: メガカイリューは**対ディアルガでは Lv1・Lv2 とも ばかぢから 38.30 のまま**（かくとうが1.6倍で通るため）で

  **1匹を1つのボスで見て「変わらない」と一般化しない**——検証は必ず実際の相手タイプで行う
- **⚠ 火力の候補キャッシュには必ずメガレベルを入れる**（2026-09-01に3か所で踏んだ）:
  火力チェッカーの `mpTopCache`（最少討伐人数の候補）・タイプ別火力の `rankCache`・
  レイドシミュの `topCache`（1位おまかせ）。ボスやタイプだけをキーにすると
  **レベルを変えても古い構成のまま**になる。実例: ルギア★6の1位おまかせが

  - したがって**「かたよっています」「バランスを取りましょう」のような良し悪しの言葉を使わない**。
    見出しも「◯◯チェック」「◯◯バランス」のように**正解からのズレを測る言い方にしない**
    （「3匹の働き」→「**得意な場面**」にしたのはこの理由）
  - 提案の機能も**足りないものを埋める形にしない**。「序盤型を探す／終盤型を探す」は
    **いつでも両方出して、どちらへ寄せるかは使う人が決める**（足りない型のときだけ出すと「揃えるべき」の意味になる）
  - **穴（3匹とも勝てない相手）だけは例外**。これは戦術の好みではなく事実として不利なので、
    数を出して入れ替え候補につなげてよい
- **「ぱっと見でわかる」を最優先にする(恒久ルール・2026-08-12確定)**:
  **「読めばわかる」は当たり前**で、目指すのは**ぱっと見でわかる**こと。全ツールの新規実装・改善に適用する
  - **判断基準**: **ポケモンGOのバトルを知り尽くしたタダシさん本人がパッと見で分からないなら、
    中級者以下には絶対に分からない**。「自分は分かるから大丈夫」は通用しない
  - 同じ内容でも読みやすさは**文字の量・色・字体・大きさ**で変わる。
    絵で伝えるときも**デザイン・色・余白・大きさ**で分かりやすさが決まる
  - **説明文を足すのは最後の手段**。まず配置・色・大きさ・余白・言葉選びで伝わらないかを考える。
    情報を足すより**削って際立たせる**方向を先に検討する
  - **数字を並べるより状況を言葉にする**（「1匹 19」→「1匹頼み 19」）。
    **分析の結果ではなく、次に何をすればいいかまで出す**
  - **シミュレーターとしての性能が一番大切**。ただし**分かりづらくて使われなければ意味がない**。
    **難しいものを簡単と思わせられるかが腕の見せどころ**
  - 失敗例（2026-08-12）: パーティ診断の円グラフ＋「3匹 10／1匹 19」は
    **匹数がふたつ並んで**どちらが何の数か読めず、タダシさん本人が
    「意味は理解できているのに頭に入らない」と評した → マスの図＋診断文へ作り直した
- **スマホの入力欄は文字16px以上にする(恒久ルール・2026-08-13確定)**:
  iOSは**文字が16px未満の入力欄にふれると画面を自動拡大し、そのまま戻らない**。
  狭い画面(540px以下)では入力欄を16pxにして**そもそも拡大させない**
  （`/gbl/` はポケモン名・検索・個体値・CPの各欄に適用済み）。全ツール共通で、新規の入力欄も同様
- **入力欄の中身を「打っている最中」に書き換えない(恒久ルール・2026-08-21確定・実機で踏んだ)**:
  日本語キーボードでは**数字も「変換中の文字」として入ってくる**ため、`input` のたびに
  `value` を書き換えると**変換が壊れて1文字も打てない**。個体値チェッカーのCP欄で実際に発生した
  （PCでは普通に打てるので、ローカル確認だけでは気づけない）。
  - **`e.isComposing` のあいだは何もしない**。整えるのは **`compositionend`** のとき
  - **全角数字は消さずに半角へ直す**（`[０-９]`→`[0-9]`）。消すと打つそばから消えて「打てない」ように見える
  - 名前検索の欄（`#q`）は最初からこの作りになっていた。**新しく入力欄を足すときは必ず同じ形にする**
- **UI**: 見やすさ・わかりやすさに常に最善を尽くす(公開前にセルフレビュー必須)
- **文字数を極力減らす(恒久ルール・2026-08-07確定)**: **絵やマークで表せるところは文字にしない**。
  UIは「文字が多くて読む気がしない・触る気がしない」状態を避けることを最優先にする。全ツールの新規実装・修正・改善に適用する
  - 使うマークは意味が自明なものだけ(🛡シールド ／ ⏱時間 ／ ⇄交代 ／ ▶発動 ／ 🎲ランダム ／ 📌固定 ／ ⏸硬直 など)。
    意味が推測できない記号を当てるくらいなら短い日本語を残す
  - **説明・仕様の文章は画面のあちこちに置かない**。**ページ最下部の「使い方」タブ1か所にまとめる**(`#helptab`/`#helpbody`)。
    画面内には結論だけを置き、理由や補足はすべてそちらへ移す
  - 数値は単位を削る(「27.0秒」→ ⏱27.0 など)。表の見出しもマークにする
  - **説明ありモードの仕込み(2026-08-13)**: 文字を減らすために画面から外した補足は**消さずに
    `class="expl"` を付けて隠しておく**（CSSで `.expl{display:none}` / **`.explain .expl{display:revert}`**）。
    のちに切り替えを作るときは、ルート要素に `explain` を付けるだけで一斉に出せる。
    第1号は「※わざは〜／あいては環境の標準構成」の注記
    - **`display:revert` にそろえた**（2026-08-14）。`block` 固定だと**行の途中に置いた補足**が
      表示モードで改行されてしまう（火力チェッカーの「（シールド中2倍補正込み・◯◯）」で該当）。
      `revert` なら `<span>` は行内・`<p>` はブロックと、元の表示種別のまま出る。/gbl/ 側も同じにしてある
  - **説明ありモードの切り替えは実装済み（2026-08-15・全7ページ）**。仕組みは上の
    「説明ありモード(💡)は共通ファイル」のセクションを参照
- **UIの統一(恒久ルール)**: 複数のツールで同じような表示・操作になるものは**なるべく統一する**。新しい画面を作る前に「他ツールに同じ役割のUIがないか」を確認する
  - 例: 絞り込みタブは**ジム挑戦と同じ「独立ON/OFFのチップ」形式**。シャドウ・メガ・ゲンシはそれぞれ独立で、両方ONなら両方がランキングに入る(火力チェッカーも2026-08-06にこの形式へ統一)。「シールド破壊(メガ)」のような別ランキングに切り替わるタブだけは例外で、押している間は他の絞り込みを無効化する

### 未実装ポケモンも図鑑・GBL・ロケット団・個体値チェッカーで選べる（2026-09-04実装・タダシさん指示）

**「データ元に入っているすべてのポケモン」を、実装前でも入力で使えるようにした**（タダシさん「動画で実装直前にめちゃめちゃ使うからいつも困る」）。
対象は**図鑑・GBL・ロケット団**（個体値チェッカーは元から `build_iv.py` が `r` を見ていないので、すでに全部入っていた＝変更なし）。
**火力チェッカー・タイプ別火力・レイド・ジム・マックスバトルには入れない**（実装済みだけを載せる従来どおり）。

- **対戦データ（`pvp_data`）は元から未実装（`r:0`）も収録していた**が、`gbl-app.js` の `KEYS` が `r` で弾いていた。
  **検索候補だけ `KEYS_ALL`**（`r:0` を含む・下の `hid` は除く）に切り替え、名前の右に**オレンジの「未実装」札**（`.unrel`）を付ける。
  **環境一覧・対策さがしの「全ポケモン」・ロケット団ランキング・入れ替え候補は従来どおり `KEYS`（実装済みだけ）**
  ——ランキングに未実装が混ざると「実際に使える最強」が読めなくなるため。選んだ未実装ポケモンは1対1・パーティ診断・
  模擬戦・ロケット団の枠で普通に計算できる（データ元の性能そのまま。未実装のわざ性能は変わることがある）
- **`hid:1`（隠す）**: バトル中だけの内部フォルム（ギルガルド(ブレード)・ミミッキュ(ばけたすがた)・ウッウ(うのみ/まるのみ)・
  モルペコ(はらぺこ)）と情報元の重複エントリ（`duplicate` タグ）は、`r:0` でも候補に出さない。
  **データ自体は残す**（`pvp-engine.js` が `aegislash_blade` を参照する）。
  **⚠ キー名を `h` にしてはいけない**——`h` は**HP種族値**で、最初に `h` にしたら全ポケモンが隠れた（実際に踏んだ）
- **図鑑（`/pokedex/`）**: `buildDex` が `r:0` も載せ（`un:1`）、一覧の行・検索候補・ヒーローカードに「未実装」札。
  **ジム・レイド側の性能は `pokedex/unreleased.json`**（`build_data.py` が除外した未実装120種を捨てずに書き出す・
  わざ定義は `godata.json` の `moves` を共用＝欠けなし）を図鑑だけが読んで `GO.pokemon` に合流する（無くても動く）。
  内部フォルムは対戦側の `hid` と同じ名前のものを載せない
- **アルセウス18フォルム・シルヴァディ18フォルムなどもすべて出る**（「すべて」の指示どおり）。
  メタモンは情報元が未実装扱いなので札が付く（ゲームには居るがバトルに出せないため）

### 新しいツールを作ったら専用アイコンとmanifestも必ず付ける（2026-08-20確定・タダシさん指摘）

`/type-dps/` と `/raid/` が**火力チェッカーのfaviconを借りたまま**で、
**スマホでホーム画面に追加すると「ポ」の文字アイコンになっていた**（apple-touch-iconもmanifestも無いため）。
他の7ツールは最初から持っていたので、**新規ツールで抜けやすい**。次に作るときは下の4点を最初から入れる:

1. **`assets/icons/<ツール名>/` に4サイズ**（`favicon-32.png` / `apple-touch-icon.png`(180) /
   `icon-192.png` / `icon-512.png`）
2. **`<ツール名>/manifest.webmanifest`**（`short_name` がホーム画面の名前になる）
3. **headに3行**（icon / apple-touch-icon / manifest）＋ **`<meta name="apple-mobile-web-app-title">`**
4. デザインの流儀は既存とそろえる: **濃い背景に、そのツールを表すシンボル1つ**
   （火力チェッカー=メーター／GBL=VS／ロケット団=R／マックスバトル=盾と剣／
   **タイプ別火力=虹色の棒グラフ**／**レイド=大きなボスに挑む3人**）
   - レイドは最初「赤〜オレンジの★」にしたが、**ただの星で汎用的すぎる**とタダシさんが却下。
     3案（タマゴ／ボスと挑戦者3人／制限時間リングと炎）から**「ボスと挑戦者3人」を選択**。
     **このツールの主役＝最低クリア人数をそのまま絵にした**のが決め手。
     ボスの表情は**つり上がった目・への字の口・牙・角**で「強そう」に（最初の笑顔では敵に見えなかった）
- **作り方**: SVGを書いて**ブラウザのcanvasでPNG化**する（このMacに `rsvg-convert` も `node` も無い）。
  ローカルにPOSTで受け取るスクリプトを立てて4サイズ書き出すのが早い
- 検証済み（2026-08-20）: くさ1位カミツルギ34.63がエクセル版の並びと一致（エクセルの55.4は
  弱点1.6倍込みの列。34.63×1.6=55.4で同値）／URLパラメータの往復／スマホ375pxで横はみ出しなし／
  PNG書き出し1980×1440

## 開発の基本

### データ更新パイプライン（2026-08-09に全ツール対応へ整備）

- **新ポケモン・新わざは必ず「全ツール」に反映する（恒久ルール・2026-08-13確定）**:
  1匹・1わざでも、**片方のツールにだけ入っている状態を残さない**。
  対戦側(/gbl/・/rocket/)とPvE側(火力チェッカー・ジム挑戦・ジム防衛・マックスバトル)は**データ提供元が別**なので、
  **一方に入っていても、もう一方は自動では入らない**（ゼラオラのプラズマフィストで実際に発生）
  - 対応するときは**そのポケモン・わざだけを直して終わりにせず、同種の漏れが他にないか必ず総点検する**
    （2026-08-13の点検で、プラズマフィストのほかに5件＝ガリョウテンセイ・きょけんとつげき・ねらいうち・
    ハイドロカノン(インテレオン)・どろかけ(パフュートン) が同時に見つかった）
  - 点検のやり方: PvPokeの `gamemaster.json` と `godata.json` を突き合わせ、
    **①わざ定義の有無 ②実装済みポケモンの習得わざの差分** を出す。
    出てきたものは**入手可能かどうかを外部攻略情報で1件ずつ確認する**
    （PvPokeの `legacyMoves` は入手不可の旧レガシー技なので**収録しない**。
    `eliteMoves` は特別枠＝収録する。ドーブルは全わざを覚える特殊枠なので除外）
  - 直したら**火力チェッカー→ジム挑戦→ジム防衛→マックスバトルの順に再生成**し、画面で表示を確認してからpushする
- **毎日朝6時(JST)に `.github/workflows/update-data.yml` が全ツールのデータを再生成し、変更があればそのままサイトへ反映する（完全自動）。反映した内容は「📢 ゲームデータの更新内容（8/13）新ポケモン1件」というIssueで知らせ、GitHubがそれをメールで送る**
  - **2026-08-12にタダシさんの指示で、承認待ちPRから完全自動へ変更した**（「更新があったら自動で反映してほしい。結果だけ報告してくれればいい」）。
    それまでは `peter-evans/create-pull-request` でPRを作り、Mergeを押したときだけ反映していたが、**毎日Mergeを押す手間をなくすため**に廃止した
  - 件名の要約は `build_data.py` が `HEADLINE:` として出す（新ポケモン／新シャドウ／種族値変更／技の追加／新しい技／威力調整／削除の件数）
  - 前回のお知らせは新しいものを立てる前に自動で閉じる。判定は件名が `📢 ゲームデータの更新内容` で始まるかどうか
    （環境リスト側の `📢 環境リストの更新結果` とは前置きを分けてあるので、互いに閉じ合わない）
  - **変更内容の確認は事後になる**（先に反映される）。おかしなデータが載った場合はそのコミットを戻す運用
- 実行順（ローカルで手動更新するときも同じ順で実行する）:
  1. `build_data.py` → `index.html`・`godata.json`（火力チェッカー。差分サマリー`changes.md`も生成）
  2. `gym-attack/build_gym.py` → `gym_data.json/js`（**godata.jsonから同期**。2026-08-09新設・それまで手作業で新ポケモンが取り残されていた）
  3. `gym-defense/build_defense.py` → `defense_data.js/json`
  4. `max-battle/build_max.py` → `max_data.js`
  5. `build_pvp_data.py` → `pvp_data.js/json`（/gbl/・/rocket/）
  6. `iv-checker/build_iv.py` → `iv-checker/index.html` の `const POKE`（個体値チェッカー。
     **pvp_data.jsonから同期**。2026-08-15新設・それまで手作業で新メガが取り残されていた）
- `gym_data.json` は手編集しない（build_gym.pyの同期で上書きされる）。表示名・並びは既存を温存し、実質変化だけ更新する安全設計
- **わざの時間は3つ持つ**（2026-08-14追加）: `godata.json` は **d=全体の長さ / w=ダメージが出るまで / we=判定終了**（秒）、
  `gym_data.json` は **dur / dw / dwe**（ミリ秒）。元は Game Master の `durationMs` /
  `damageWindowStartMs` / `damageWindowEndMs`。**ジム防衛のおすすめわざ選びが d と w の両方を使う**
  （じしんは d=3.5秒でも w=2.6秒で先にダメージが出る＝重いわざと区別できる）。
  `SUPP_MOVES`（GM未収録の手動補完わざ）にも `damageWindowStartMs` / `damageWindowEndMs` を書くこと。
  **おんがえし だけは元データに `damageWindowStartMs` が無い**ので `damageWindowEndMs` で代用している
- **威力0のわざも収録する**（はねる・へんしん・あくび。2026-08-14追加）。火力計算では0として扱うだけだが、
  性能データは欠けなく持っておく方針。ただし**ポケモンが実際に覚えるものに限る**
  （条件を外すと内部用の未実装データ `VN_BM_001` 等を64件拾ってしまう。実際に踏んだ）
- **新メガの取りこぼし防止**: Game Masterの`tempEvoOverrides`に載らない新メガ（メガエアームド・メガライチュウX/Y・メガタイレーツで実際に発生）は、`build_data.py`がPvPoke側から自動補完する。手動テーブル`MANUAL_MEGA`は最後の保険
- **実装前（released=false）のポケモンは自動補完に入らない**（2026-08-15判明）。PvPokeフォールバックは
  `if not sp.get('released'): continue` で弾くため、**実装間近のものは `MANUAL_MEGA` に手で入れる**。
  タダシさんから「もうすぐ実装される」と指示が出たらこの対応をする
  - 実例: **メガブリガロン・メガマフォクシー・メガゲッコウガ**（カロス御三家メガ）。
    対戦側(`build_pvp_data.py`)は released を弾かないので**/gbl/・/rocket/ には最初から入っていた**＝
    **PvE側だけ取り残される**という形で差が出る。**片方に入っていたら、もう片方を必ず確認する**
  - **わざは元ポケモンのものをそのまま引き継ぐ**（メガは元と同じわざを覚える）。
    ハードプラント・ハイドロカノン等の特別わざも一緒に付いてくる
  - `MANUAL_MEGA` から作るときも **`fe:1`（最終進化）を付ける**。付け忘れると火力チェッカーの
    絞り込みで扱いがずれる（2026-08-15に追加）
- **シャドウ実装が情報元に追いつかないときは `MANUAL_SHADOW` で先行反映する**（2026-09-08新設）:
  シャドウかどうかの判定は、両ビルドとも**対戦データの `<key>_shadow` エントリがあるか**だけで決まるので、
  ゲームで実装されても情報元が追随するまで反映されない。**`build_data.py`（大文字キー）と
  `build_pvp_data.py`（小文字キー）の両方に同じ顔ぶれを書く**——片方だけだとPvE側かGBL側だけ反映される。
  提供元に入れば自動でも拾う（集合に足すだけ）ので、**消さずに残しておいてよい**。
  2026-09-08の登録: ゼクロム／カリキリ・ラランテス／スナバァ・シロデスナ／コソクムシ・グソクムシャ
- **⚠ シャドウを付けたポケモンは `gym_data.json`・`max_data.js` の「わざの並び順」も最新にそろう**。
  どちらも「実質変化があったときだけ書き直す」温存設計なので、shadowが変わったのをきっかけに
  古い並びが現在のものへ更新される（**顔ぶれは同じ・順序だけ**）。ジム防衛のおすすめわざは
  同点のときソートの安定性で順が決まるため、**併記の1本目と2本目が入れ替わることがある**
  （2026-09-08はスナバァ・シロデスナが「シャドーボール or だいちのちから」→「だいちのちから or シャドーボール」。
  どちらもスコア120の同点で中身は変わらない）
- **ジム防衛（`/gym-defense/`）とマックスバトル（`/max-battle/`）にメガは入らない**——
  メガはジムに置けず、マックスバトルにも出せないため。**この2つは「メガが無い＝正しい」**ので、
  新メガを全ツール展開するときの対象は**火力チェッカー・ジム挑戦・/gbl/・/rocket/・個体値チェッカー**の5つ
- **Game Master提供元は2026年4月〜8月のあいだ更新が止まっていた（2026-08-13発覚 → 2026-08-29に再開）**:
  再開後も**新わざの収録は追いついていない**（プラズマフィスト・きょけんとつげき・ねらいうち・ダイビング・
  オーラぐるま・ダイマックスほうは2026-09-02時点でも未収録）ので、下の手動補完は引き続き必要。
  そのため止まっていた期間に実装された新わざは
  **わざ定義ごと自動更新に入ってこない**（プラズマフィスト・きょけんとつげき・ねらいうちで実際に発生）。
  対策として `build_data.py` の **`SUPP_MOVES`**（わざ定義の注入・`apply_gm_supp()`）と既存の
  `SUPP_EC`/`SUPP_C`/`SUPP_EQ`（習得の追加）で手動補完する。提供元に正式収録されたら自動取得値を優先する設計。
  **新わざのPvE数値の裏取りは外部レイドシミュレーターのAPI**（`https://fight.pokebattler.com/moves`・
  実ゲームデータ準拠）を使う。攻略サイトの表示値はタイプ一致1.2倍込み・ゲージ欄がPvP値の使い回しのことがあるので注意。
  対戦側(/gbl/・/rocket/)はPvPoke由来なので影響なし。
  **入手不可の旧レガシー技**（ラッキーのサイケこうせん等）は従来どおり収録しない
- **日本語名が取れない技（`◯◯_PLUS`等のゲーム未実装データ）は`build_pvp_data.py`が収録しない**（英語名のまま「その他のわざ」欄に並ぶのを防ぐ）
- `max-battle/latest.json` はGame Masterのキャッシュ（18MB超）。gitignore済み・コミットしない

### シーズンのわざアップデート（3か月ごと・2026-09-02確定・タダシさん指示）

**新シーズンの切り替わりのたびに大型のわざ調整が来る**（威力の変更・メーターの調整・新しく覚えるわざ）。
毎回同じ手順で受けられるように、公式発表の内容を **`season_moves.py`** に書き写して突き合わせる形にした。

- **公式が数字で出すのは威力だけ**。メーター（SPアタックの消費ゲージ・ノーマルアタックの獲得ゲージ）は
  「チャージされやすく／にくくなります」としか書かれない。
  **⚠ したがって発表を見て手でデータを書き換えてはいけない**——威力だけ入れてゲージを据え置くと
  **実在しない性能のわざ**になる（しおみず60→100をゲージ50のまま入れると、ありえない性能で全ツールが計算する）。
  正しいやり方は**提供元のデータが入るのを待ち、入ったことをチェッカーで確かめる**こと
- **`season_moves.py` は書き換えない受け皿**: `SEASON`（シーズン名と開始日）・`MOVE_CHANGES`（わざの性能変更）・
  `NEW_LEARNS`（新しく覚えるわざ）の3つの表を持ち、いまの `pvp_data.json` / `godata.json` と突き合わせて
  **✅反映済み／⏳未反映／⚠想定外** を出す。`build_pvp_data.py` の最後から呼ばれ、
  未反映があれば `changes.md` に追記される＝**毎朝のお知らせメールに出る**ので、反映された日にすぐ気づける
- **⚠想定外＝わざIDの対応づけを間違えている**（または、もう反映済みなのに旧値を書いている）。
  表を書いた直後にチェッカーを流し、**「旧」の値がいまのデータと全部一致する**ことを必ず確かめる
  （ここが一致すれば、対応づけが正しいことの裏取りになる）
- **ノーマルアタックはPvEとPvPでIDが違う**（ジム・レイド側は末尾が `_FAST`。かみつく＝`BITE` / `BITE_FAST`）。
  ポケモンのキーも別体系（対戦は小文字 `muk_alolan`・PvEは大文字 `MUK_ALOLA`）なので、表は両方持つ
- **シーズン開始は日本時間10:00**。朝6時の自動更新だけだと丸1日ぶん古い性能で計算してしまうので、
  **`update-data.yml` に JST 11:00 の回を足してある**（変化が無い日は何もしないので、増えるのは実行だけ）

**2026-09-09「黄昏の旅路」での実績（初回運用の記録）**:

- **対戦側（`pvp_data`）は提供元がシーズン当日の朝6時の自動更新で追いついた**（威力27件・ゲージ・能力変化・新規習得42件すべて）。
  公式は数値を出さないメーターも、攻略サイトの実測値（10まんばりき60→55等）と提供元の値が全件一致した
- **ジム・レイド側（`godata`）は提供元が8/29で止まったまま**だったので、`build_data.py` の手動補完で先行反映した:
  **`SUPP_C_2609`／`SUPP_Q_2609`**（新規習得42件＝`SUPP_C`/`SUPP_Q` へ合流。既にあれば足さないので提供元が追いついても害なし）と
  **`MOVE_FIX`**（サイコブースト 威力70→130・ゲージ2本→3本。**`when` の値が取得値と一致するときだけ上書き**するので、
  提供元が新しい値に更新した瞬間に自動で効かなくなる）。メガはリスト実体を共有しているので元ポケモンへ足せば自動で付く
- **⚠ 対戦側は本体キー（`toxtricity`）にしか新わざを足さず、フォルム違い（amped/low_key・未実装扱い）は取り残す**。
  `build_pvp_data.py` の **`MANUAL_LEARN`** で補う。`season_moves.py` の突き合わせは本体キーで見る
- **⚠ 新ポケモンが実装された週は、提供元（8/29の版）の習得わざが誤っていることがある**: マフィティフ・オラチフは
  「しっぺがえし」ではなく**「サイコファング」**（対戦データ・攻略サイト2か所で一致）。`FORM_MOVE_FIX` で外し `SUPP_C_2609` で足した
- **環境上位リスト（`meta_lists.js`）は翌週月曜まで前シーズンのまま**。わざの性能が変わったポケモン
  （じならし・しおみず・のしかかり持ち等）は**確定値（`answer_key.js`）の見直しが要る**＝タダシさんの判断待ち

**⚠ 反映漏れを絶対に出さない（2026-09-10タダシさん指示・恒久ルール）**:
「今シーズンの新わざが模擬戦に反映されていない」と報告された。**データ（わざ欄の候補）には全ツールで入っていた**が、
**環境上位のポケモンは人が確定した構成（answer_key.js）で戦うので、新わざも性能変更も一切使われていなかった**
（ルギアの だいちのちから・デスカーンの エナジーボール など）。GBLでは致命的なミスになる。

- **データを直しても確定構成は自動では変わらない**。だから `season_moves.py` の `review_confirmed()` が
  **確定構成の見直し候補**（そのポケモンが新しく覚えたわざ／性能が変わったわざを使っている行）を毎回出し、
  `changes.md`（＝毎朝のお知らせ）にも追記する。**シーズンが切り替わったら、この一覧を必ずタダシさんに見せて判断を仰ぐ**
- 2026-09-10時点の見直し候補は70件（新しく覚えた3件・性能が変わった67件）。**2026-09-11に見直し完了**:
  情報元のシーズン後の推奨と比べて、同じ41件とメガミュウツーY（カップ専用）は据え置き、違った28件のうち26件を情報元の推奨へ
  （アーマーガア→アイアンヘッド・ルギア→だいちのちから・ネクロズマ2種→あくのはどう 等）。
  **マスターのコノヨザル（通常/シャドウ）はタダシさん指示でけたぐりのまま**（情報元はカウンター）。
  **次のシーズンも「情報元の今の推奨と同じ／違う」に仕分けて、違うものだけ見せると早い**

**次のシーズンでの手順**:

1. 公式ニュースの「わざの変更」「覚えられるわざの変更」を読む（**攻略サイトのまとめは誤りが混じる**——
   2026-09の回は、ヘルガーのやきつくすをSPアタック・アーボックのまきつくをノーマルアタックと書いていた。
   **公式の本文だけを写す**）
2. `season_moves.py` の3つの表を丸ごと書き替える（前シーズンぶんは消してよい）
3. `python3 season_moves.py` で「旧」の値が全部一致することを確かめる（⚠が出たら対応づけを直す）
4. シーズン開始後にパイプラインが回り、全項目が ✅ になるのを確かめる。
   **開始から数日たっても⏳が残るなら提供元が遅れている**ので、そのときタダシさんへ報告して判断を仰ぐ
